## 本批可见结果

既有保存核对入口改为“核对当前申请”。用户主动查询后，使用已有 current GET，验证原核对码/摘要、申请与患者身份、完整逻辑管/实管/分析关联，展示本次查询时的患者、生日、待采集/已采集/已取消、实管作废/拒收及实管状态编号。原始首次回执仍单独保留，不用它的 REQUESTED 状态冒充今日状态。

- 同类型多管、同排序追加管和同项目多分析按真实 ID 保留；缺管、漏分析、错归属、未知逻辑状态或关联不完整时拒绝整份结果，不呈现部分成功。
- Current 各层只投影已验证事实字段，不透传任意操作能力或步骤指令。事件只接受后端 UTC 格式及真实日历日期；生日作为日期原样展示，不转换时区。
- 当前查询复用已有授权、工作区、会话和暂停代数保护。查询超时、409、部分响应、切换会话不清核对标记、不覆盖当前草稿、不发送保存或旧查号请求；迟到结果不能重新出现。
- 物理状态不等同于采集状态。即使作废/拒收标志都为否，仍显示物理状态编号，不推断“正常”。类型与物理状态名称仍需从有效主数据解析，当前明确标为编号/名称待映射；这是未交付项，不能让用户靠记编号开展日常业务。
- 本版本明确告知只读及尚不能恢复采集/编辑；没有“采用”“继续采集”或隐藏清标记操作。没有恢复成功后静默跳转。

## 新确认的恢复阻断与下一步

受控 HEAD `2e6f3542a` 的 `OrderCollect` 在存在任一实管时跳过待采集请求读取，并使用旧 `loadOrder(labNo,false)` 和整张申请的 `saveOrder()`；保存后进入后续步骤。当前只读 DTO 并不包含完整项目计划、EQA、送检方/医生、知情同意、环境字段及采集前置进度。

因此，直接将 current 的患者/管记录填入默认表单、解除保护并进入上述旧保存链，可能丢失待采集管，或用缺省/陈旧字段覆盖原申请资料。本批不以“界面能点了”作为安全恢复依据，也不拼接两个旧 GET 伪造一致快照。

工作树中已有 collection-only 写入、请求 ID 绑定和更完整加载保护，但它们属于大量历史未提交修改，尚不是本批独立候选已验证能力。**下一主批先沿用并收口现有采集专用写入与显式请求绑定链**：只提交采集字段，不改患者/申请资料；验证剩余管、错管、重复提交、取消/作废/拒收、失效权限及失败回滚。随后在同一 current 读取边界补齐必要的采集上下文、有效主数据名称与前置条件，明确确认采用后才恢复可操作状态，并禁用旧整单加载/写入回退。不得重做已经完成的回执/事务工具或另开菜单主批。

上述后续仍需获准隔离库验证保存→刷新核对→部分采集→再次恢复及并发/撤权。新发现的是已验证候选的产品恢复阻断，不是已经证明真实患者资料被修改。本批未改变任何真实患者数据。
