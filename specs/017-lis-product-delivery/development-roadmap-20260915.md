## 执行规则

1. **每批只完成一项可说明、可回退的功能。** 开始时明确实际入口、复用代码、验收场景及依赖，先检查当前代码是否已经实现，避免重复开发。
2. **完成后自测，再提交。** 验证相关单元/集成用例、语言键、类型基线和正式构建；涉及界面时检查真实组件的模拟浏览器操作，涉及持久化时补事务、权限、并发和隔离数据库验证。模拟通过不写成医院现场通过。
3. **本批引入或影响的失败先修复。** 全量项目历史问题按同一干净基线对照、独立登记；仅通过局部用例不代表发布门禁通过。构建环境阻断、未执行项目及真实现场依赖必须记入验收记录。
4. **只提交验证过的本批差量。** 仓库当前存在大量历史未提交修改，使用干净候选验证；提交前核对源文件、暂存文件和受测候选一致。禁止全量暂存历史修改、覆盖用户修改或提交临时数据及密钥。
5. **提交说明包含功能和验证。** 使用 `feat` / `fix` / `docs` 等清晰标题，正文写明验收范围、限制和证据。完成记录标注提交号；不把“开发已验”升级为“部署完成”。远程推送、运行版更新和现场切换另外执行。

## 界面改造的统一范围

八个一级菜单固定为：01 今日待办、02 申请与采样、03 标本签收、04 检验与审核、05 质量与异常、06 查询与报告、07 接口中心、08 基础配置。无权限的工作区不补空菜单，编号保持稳定。

各页按“当前队列 → 所选对象详情 → 下一步操作”组织。先改业务主线实际使用的页面，再改低频管理页。复用 Carbon 和现有 React Intl；路由、后端权限和报告打印样式分别验证。菜单统一完成不等于每个业务页均已改造。

## 技术路线

近期继续使用现有 Java / Spring 后端和 React 前端，以清晰模块边界推进，保持业务 API 与数据关系稳定。现仓库是传统 Spring WAR，不能写成已经完成 Spring Boot。

Spring Boot 迁移建立单独任务和兼容性候选：检查初始化、安全链、事务、插件、任务调度、配置和部署，验证相同业务回归后再切换。多实例扩容先解决共享状态、任务领取、幂等和数据库连接预算；微服务只在确有独立部署或负载隔离需求时拆分，不作为本轮界面与业务改造的前置条件。

## 如何判断进度

每批使用“待开始 / 开发中 / 自测中 / 开发已验并提交 / 已部署 / 现场已验 / 阻断”状态。完成一个按钮或一组模拟用例，不给整个 LIS 填估算完成百分比。

每笔提交附验收记录：基线、改动范围、运行的检查与最终结果、浏览器/数据库的真实或模拟条件、未通过或未执行项、下一任务。报告与接口等大项在代码审查后拆出子批，不提前承诺无法核实的完成日期。

当前可持续推进的工作不依赖医院设备到场。进入相应现场批次前，需提供：首期科室/专科及岗位规则、报告分组与更正规则、主数据、报告/标签样张、设备协议、HIS 合同、峰值与恢复目标、验收责任人。以明确标识的模拟资料先验证技术流程，随后按真实资料完成现场验收。
