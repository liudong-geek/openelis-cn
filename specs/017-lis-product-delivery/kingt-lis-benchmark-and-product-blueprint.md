# 金唐 LIS 对标研究与 OpenELIS 中国医院版产品方案

> 版本：v1.0  
> 日期：2026-08-17  
> 用途：产品立项、范围评审、研发排期、医院试点验收  
> 结论口径：公开资料调研 + 当前代码库审计，不替代金唐厂商现场演示和医院用户访谈

## 1. 执行摘要

公开资料中能够被核实的产品是**宁波金唐软件有限公司的“金唐临床检验管理信息系统（LIS）”，产品描述中称 EG2000 LIS**。用户所说的“金塘 LIS”应当是“金唐 LIS”的同音或文字误差。

金唐公开产品描述的核心不是单点功能，而是中国医院场景下的连续业务链：医生申请、护士执行、样本标识与采运、检验质量控制、结果修正、报告、收费、资料查询、岗位权限以及 HIS 连接。它的主要竞争力可以概括为：**医院本地化、临床协同、收费协同和责任闭环**。

当前 OpenELIS 代码库并不缺少 LIS 的技术功能。它已经拥有患者与订单、电子订单、条码、样本管理、工作计划、结果录入、结果验证、报告、分析仪、室内质控、室间质评、不符合项、库存、存储、转诊、病理/细胞学/免疫组化、FHIR、权限和审计等大量能力。其优势是开放、标准化、质量体系强、样本与专业实验室能力深；其主要问题是：

1. 功能以模块存在，但还没有组成中国医院用户可连续完成的产品闭环。
2. HIS、住院/门诊/体检、科室/病区/床位、收费和护士站协同不足。
3. 危急值、样本拒收重采、报告修订撤回等关键事件缺少临床端闭环。
4. 新旧页面和入口并存，状态、主操作和下一步不一致。
5. 中文只是界面翻译的一部分，业务字典、报告模板、接口码表和实施资料仍需本地化。

因此，推荐方案不是“仿制一套金唐界面”，而是建设 **OpenELIS 中国医院版**：保留 OpenELIS 的实验室、质量、分析仪、FHIR 和开源底座，新增中国医院交付层——角色工作台、统一状态机、标本事件链、危急值闭环、报告版本、接口网关、收费事件和中文主数据包。

产品判断：**可以在当前项目基础上开发适配，但现在还不能作为成熟国产医院 LIS 直接替换上线。** 在单院试点范围内补齐 P0 闭环后具备交付价值；医院外围系统、电子签名、消息通知和收费结算应优先外部对接，不应全部重做进 LIS。

## 2. 调研对象、证据和限制

### 2.1 身份核实

- 金唐官网确认宁波金唐软件有限公司长期从事医疗卫生信息化，产品覆盖智慧医院、智慧卫生、县域医共体、云 HIS 等领域。
- 公开软件市场存在“金唐临床检验管理信息系统（LIS）”独立条目，厂商标注为宁波金唐软件有限公司，正文将产品称为 EG2000 LIS。
- 未发现厂商公开的最新版 LIS 用户手册、完整菜单、演示环境或接口规范。因此，不能把所有国产 LIS 的采购要求都直接归属于金唐。

### 2.2 证据等级

| 等级 | 含义 | 本方案使用方式 |
| --- | --- | --- |
| A：公开确认 | 金唐产品页或金唐官网明确描述 | 可直接写入“金唐能力” |

## 3. 金唐 LIS 主要功能研究

### 3.1 金唐公开确认的能力

| 业务域 | 公开确认内容 | 产品价值 |
| --- | --- | --- |
| 检验申请 | 医生提出检验项目申请 | 申请来源与临床诊疗连接 |
| 医嘱执行 | 护士工作站执行检验申请医嘱 | 把 LIS 流程前移到临床科室 |
| 样本管理 | 样本标识、采集、运送 | 降低错采、漏采、错送风险 |
| 仪器管理 | 检验仪器系统保养维护 | 将设备责任纳入科室运行 |
| 室内质控 | 检验项目室内质量控制 | 结果发布前建立质量约束 |
| 结果管理 | 结果修正 | 支持差错修正与责任追溯 |
| 报告服务 | 缩短报告周期，快速提供检验结果报告 | 提升临床可获得性和 TAT |
| 行政管理 | 行政管理和岗位分工 | 明确人员责任和权限 |
| 收费管理 | 检验收费管理 | 与医院经济业务协同 |
| 数据服务 | 资料储存、查询 | 支持临床查询和历史追溯 |
| 系统集成 | 与 HIS 有效连接 | 避免重复录入，打通订单与报告 |
| 临床沟通 | 检验科与医生、护士工作站沟通平台 | 形成检验前、中、后的跨部门协同 |

### 3.2 从公开描述推导出的产品结构

以下是对金唐公开能力的产品化归纳，不代表其公开页面逐项给出了相同菜单名称：

1. **检验前**：HIS 医嘱、医生申请、护士执行、样本标识、采集、运送。
2. **检验中**：样本处理、仪器作业、室内质控、人员岗位责任。
3. **检验后**：结果审核与修正、报告、查询、临床获取。
4. **科室管理**：仪器维护、行政管理、权限、收费、资料管理。
5. **医院协同**：HIS、医生站、护士站与检验科之间的消息和状态交换。

### 3.3 成熟国产 LIS 的行业基准

国家指南和医院采购要求通常会在金唐公开描述之外继续要求：

- 接收 HIS、EMR、体检系统申请，携带门诊号/住院号、科室、病区、床位、诊断、申请医生、急诊、费用等信息。
- LIS 本地开单、拼音或代码快速选项、Excel 批量申请。
- 按项目合管，提示采样管类型、颜色、数量、采集注意事项。
- 采集、运送、签收、拒收、重采、上机、留存、领用、归还和销毁的全过程追踪。
- 条码连续扫描、批量签收、补打和作废。
- 仪器单向/双向通信、工作单或工作列表下发、自动接收结果。
- 手工/批量录入、参考范围、高低值、历史对比、Delta Check、复检和自动审核。
- 技术审核、临床审核、报告发布、撤回、修订、打印和临床推送。
- 危急值发现、通知、确认、处理、超时升级和关闭。
- 室内质控、室间质评、不符合项、纠正预防措施、TAT 和质量指标。
- 收费确认、计费触发、退费/撤销、对账和费用统计。
- 用户、角色、科室、项目、组合、样本、试管、参考范围、危急值和接口码表维护。

这些能力应作为本项目的**交付基准**，而不是简单复制某个厂商的菜单。

## 4. 当前 OpenELIS 功能盘点

### 4.1 已有强能力

| 领域 | 当前源码能力 | 判断 |
| --- | --- | --- |
| 患者 | 患者登记、查询、历史、结果查看、患者合并、多标识 | 底座较强 |
| 订单 | 手工开单、电子订单、批量开单、修改订单、条码打印 | 功能存在，入口仍需收敛 |
| 样本 | 采集、样本管理、分装、转诊、运输、存储、移动、处置 | 深度优于一般基础 LIS |
| 检测计划 | 按科室、项目、组合、优先级生成工作计划 | 可复用 |
| 结果 | 手工结果、分析仪结果、计算结果、反射规则、多种查询 | 能力丰富但界面分散 |
| 验证 | 结果验证、按订单/区间/日期处理 | 存在但与报告未形成统一工作台 |
| 报告 | 常规报告、研究报告、患者报告、TAT、审计报告 | 模板较多，发布/修订状态需增强 |
| 分析仪 | 插件、ASTM、HL7、文件、字段映射、串口/桥接、错误面板 | 技术底座强，仍需逐设备验收 |
| 室内质控 | 控制批次、统计、Westgard 规则、Levey-Jennings 图、违规告警 | 明显优势 |
| 室间质评 | EQA 项目、分发、参与者、订单和结果 | 明显优势 |
| 质量事件 | 不符合项、纠正措施、提醒、审计 | 明显优势 |
| 库存 | 物品、批次、接收、消耗、库位、预警 | 可继续产品化 |
| 专业流程 | 病理、细胞学、免疫组化、项目病例、实验室笔记本 | 覆盖面广 |
| 互操作 | FHIR R4、OpenMRS/国家系统思路、转诊和数据交换 | 标准化优势 |
| 安全 | 角色权限、审计、SAML/SSO 能力、加密部署 | 企业底座可用 |

### 4.2 中国医院交付缺口

| 缺口 | 当前表现 | 业务影响 |
| --- | --- | --- |
| 就诊上下文 | 患者强，但门诊/住院/体检、病区、床位、就诊状态模型不完整 | 医嘱无法自然落到医院场景 |
| HIS 接口产品化 | FHIR 底座强，但缺少中国医院常用 HL7 v2/REST/视图适配、消息台账和码表配置 | 每家医院都可能变成定制开发 |
| 护士站与采血中心 | 缺少面向病区护士、门诊采血的任务工作台、队列和交接 | 检验前流程无法闭环 |
| 样本拒收重采 | 有不符合项和样本功能，但拒收通知申请者、重采任务和关闭不连贯 | 临床不知道下一步做什么 |
| 危急值闭环 | 有告警和规则基础，但未看到完整的接收人、确认、处理反馈、超时升级、关闭链 | 医疗安全不满足交付要求 |
| 收费闭环 | 有支付状态/账单参考及可选 Odoo 思路，但不是中国医院的计费、退费、冲正和对账 | 无法独立进入医院生产 |
| 报告生命周期 | 有生成/验证/打印，但发布、撤回、修订版本、电子签名、临床回执需要加强 | 报告责任链不完整 |
| 自动审核 | 参考范围、规则、计算和反射基础存在，但 Delta Check、复检规则、自动审核解释与拦截需统一 | 检验员效率和安全性不足 |
| 微生物 | 代码中存在细菌学旧菜单和结果入口，但未见成熟的培养、鉴定、药敏、菌株和院感闭环 | 综合医院专业覆盖不足 |
| POCT | 未形成设备、操作者资质、质控和结果回传的独立闭环 | 无法覆盖床旁检验 |
| 中文产品化 | 已有简体中文入口，但主数据、报告模板、业务术语、帮助和错误消息仍有英文/海外语境 | 培训成本高，影响交付 |
| 一致交互 | 新旧 React/JSP、多个结果和验证入口并存 | 用户难以判断当前状态和下一步 |
| 运维交付 | Docker、日志和监控基础存在，但医院级备份恢复、灾备、巡检、接口监控和交付脚本未闭环验收 | 上线后风险不可控 |

## 5. 深度功能对标矩阵

状态说明：

- **确认**：金唐公开页明确描述。
- **基准**：行业成熟 LIS 通常要求，但未被金唐公开资料直接证明。
- **可用**：当前源码已有较完整实现。
- **部分**：存在底座或入口，但流程、体验或医院适配不完整。
- **缺口**：未发现可交付的闭环实现。
- **优势**：OpenELIS 相对传统基础 LIS 更强的能力。

| # | 能力 | 金唐公开/行业基准 | 当前 OpenELIS | 差异与决策 |
| --- | --- | --- | --- | --- |
| 1 | HIS 医嘱接收 | 金唐确认 | 部分：FHIR/电子订单存在 | 建接口网关，支持 HL7 v2、REST、FHIR 和院方私有协议 |
| 2 | LIS 手工开单 | 基准 | 可用 | 保留并统一为一个新建订单入口 |
| 3 | 门诊/住院/体检上下文 | 基准 | 部分 | 增加就诊、病区、床位、患者类型和来源模型 |
| 4 | 医生/护士医嘱执行 | 金唐确认 | 缺口 | 通过 HIS/护士站任务接口实现，不重做医生站 |
| 5 | 项目合管与试管规则 | 基准 | 部分 | 增加项目—样本—试管—采集量合并规则 |
| 6 | 条码打印/补打/作废 | 基准 | 可用/部分 | 统一标签模板、打印状态和补打审计 |

| 8 | 样本采集记录 | 金唐确认 | 可用/部分 | 统一采集人、时间、地点、异常和连续扫码 |

| 15 | 双向工作列表下发 | 行业基准 | 部分 | 已有协议规划与部分实现，按设备验收双向链路 |

| 17 | 参考范围与高低标识 | 行业基准 | 可用 | 补齐中国人群、年龄、性别、孕周等参考区间主数据 |
| 18 | 计算、反射、复检 | 行业基准 | 优势/部分 | 复用规则底座，增加可解释拦截和复检任务 |

| 31 | TAT 与质量指标 | 行业基准 | 可用/部分 | 从报表升级为实时 SLA、超时提醒和责任节点分析 |
| 32 | 仪器保养维护 | 金唐确认 | 部分 | 补设备台账、校准、维护计划、停机和放行记录 |
| 33 | 库存/试剂批次 | 行业基准 | 优势/部分 | 复用库存，联动试剂批号、质控和检测批次 |
| 34 | 检验计费 | 金唐确认 | 缺口 | LIS 管收费事件，不在内部重建医院财务结算 |
| 35 | 科室行政与权限 | 金唐确认 | 可用 | 按中国岗位重新设计角色包和最小权限 |
| 36 | 审计追踪 | 行业基准 | 优势 | 补充医院审计查询和导出模板 |
| 37 | 统计与主任办公 | 金唐确认数据查询/行业基准 | 部分 | 增加工作量、TAT、拒收、危急值、质控和成本看板 |
| 38 | 微生物 | 行业基准 | 部分/旧功能 | 若目标为综合医院，需独立产品流重新建设 |
| 39 | 病理/细胞学/IHC | 非金唐公开重点 | 优势 | 作为 OpenELIS 差异化专业能力保留 |
| 40 | 区域转诊/医共体 | 金唐公司级能力/行业基准 | 优势/部分 | 用 FHIR、转诊、运输底座建设区域样本与报告协同 |
| 41 | 标准互操作 | 金唐确认 HIS 对接，协议未知 | 优势 | 保留 FHIR，同时补齐国内常见 HL7 v2 和私有适配 |
| 42 | 中文与本地规范 | 金唐天然优势 | 部分 | 建中国主数据包、报告模板、角色术语和实施工具 |
| 43 | 任务化界面 | 公开资料未知 | 部分，已完成首页和导航首轮改造 | 继续完成订单—结果—审核—报告统一交互 |
| 44 | 开源和可扩展性 | 商业闭源产品通常受厂商约束 | 优势 | 保持核心标准化，医院差异放在配置和适配器层 |

### 5.1 对标结论

**OpenELIS 已经领先或具备优势的领域**：室内质控、室间质评、不符合项/CAPA、样本存储层级、转诊与运输、病理/细胞学/IHC、FHIR、开源扩展、权限审计。

**与金唐和成熟国产 LIS 的关键差距**：HIS 本地化、护士站和采血、就诊/病区/床位、样本签收拒收重采、危急值、收费、报告生命周期、设备维护、中文主数据和统一交互。

**最关键的产品问题**不是功能数量少，而是医院关键事件没有形成跨角色的“发起—处理—确认—关闭—审计”闭环。

## 6. OpenELIS 中国医院版产品方案

### 6.1 产品定位

面向中小型综合医院、专科医院、县域医共体中心实验室和区域检验中心，提供：

- 单院临床检验闭环；
- 多实验室样本转诊和区域协同；
- 可配置分析仪接入；
- ISO 15189 导向的质量管理；
- 无许可证锁定、可本地部署、可持续二次开发的 LIS 底座。

首个试点不建议同时覆盖所有三甲医院复杂场景。建议先覆盖临检、生化、免疫、凝血、尿液等常规专业组；微生物、POCT、血库和全院采血叫号作为后续独立域建设。

### 6.2 目标用户与工作台

| 角色 | 首页首先看到什么 | 核心操作 |
| --- | --- | --- |
| 开单/客服人员 | 未完成订单、接口失败、患者匹配异常 | 新建、补录、合并、撤销 |
| 护士/采血员 | 待采、急诊、特殊采集、重采任务 | 核对、采集、打印、交接 |
| 样本接收员 | 待签收、超时运输、异常样本 | 批量签收、拒收、重采、分发 |
| 检验员 | 待检测、仪器异常、待复检、质控状态 | 上机、录入、复检、提交审核 |
| 审核员 | 待审核、危急值、规则拦截、退回项 | 审核、退回、危急值发起、发布 |
| 科主任 | TAT、拒收率、危急值、失控、工作量 | 监控、审批、追踪纠正措施 |
| 接口/设备管理员 | 消息积压、失败重试、设备离线、未映射代码 | 映射、重放、测试、停用 |
| 系统管理员 | 用户、角色、字典、审计、备份 | 配置、授权、巡检、恢复 |

### 6.3 产品功能架构

1. **统一任务中心**：按角色展示待办、异常、超时和下一步。
2. **检验申请中心**：电子医嘱、手工开单、批量导入、患者与就诊匹配、收费状态。
3. **采样与接收中心**：合管、条码、采集、运输交接、签收、拒收、重采、分发。
4. **检测工作中心**：工作计划、分析仪、手工结果、复检、稀释、计算和反射。
5. **审核与报告中心**：技术审核、临床审核、危急值、发布、撤回、修订、签名、回传。
6. **质量安全中心**：IQC、EQA、不符合项、CAPA、TAT、质量指标、设备维护。
7. **样本与物资中心**：分装、存储、借用、归还、销毁、库存、批次、效期。
8. **接口运营中心**：系统配置、码表映射、消息台账、重试、对账、监控和告警。
9. **平台管理中心**：机构、科室、用户、角色、项目、组合、样本、试管、参考范围、模板、审计。

### 6.4 统一业务状态机

建议订单和样本使用可审计事件驱动状态，而不是由页面自行判断：

`已申请 → 待采样 → 已采样 → 运输中 → 待签收 → 已签收 → 已分发 → 检测中 → 待审核 → 已审核 → 已发布 → 已归档`

异常分支：

- `待采样 → 采样失败/取消`
- `待签收 → 已拒收 → 待重采 → 已重采`
- `检测中 → 仪器异常/待复检`
- `待审核 → 已退回 → 检测中`
- `已审核 → 危急值待确认 → 已确认/已升级`
- `已发布 → 已撤回/已修订 → 已重新发布`

每次状态变化必须记录：对象、原状态、新状态、操作人、岗位、时间、地点、原因、外部消息号和关联证据。

### 6.5 七个必须闭环的事件

1. **电子医嘱**：接收—校验—映射—建单—回执—取消/变更。
2. **样本拒收**：拒收—原因—通知—重采—重新签收—关闭。
3. **危急值**：发现—复核—通知—确认—临床处理反馈—超时升级—关闭。
4. **报告修订**：申请—授权—生成新版本—撤回旧版本—重新发布—临床通知。
5. **分析仪异常**：接收失败—隔离—人工处理/映射—重放—结果匹配—关闭。
6. **质控失控**：失控—阻断患者结果—原因调查—纠正措施—放行—审计。
7. **收费事件**：收费确认—允许执行—取消/退费—报告状态联动—对账。

## 7. 外部对接方案

### 7.1 建设原则

- OpenELIS 内部使用统一领域模型；医院差异放在接口适配器和码表配置层。
- 每条外部消息必须可查询、可重试、可对账，禁止只写接口日志文件。
- 所有写入使用幂等键，建议为 `来源系统 + 消息类型 + 外部业务号 + 版本号`。
- 外部系统暂时不可用时，核心检验流程应允许受控降级和补偿。
- FHIR 是内部标准能力，但不能要求所有国内医院先改造成 FHIR 才能接入。

### 7.2 接口清单

| 外部系统 | 入站 | 出站 | 推荐方式 |
| --- | --- | --- | --- |
| HIS/EMR | 患者、就诊、医嘱、取消、科室、医生、费用状态 | 接收/拒收/检测/报告状态、结果、报告、危急值 | HL7 v2、REST、FHIR，私有接口做适配器 |
| 护士站/采血系统 | 待采任务查询、采集确认、交接 | 拒收、重采、特殊采集提醒 | REST/消息队列 |
| 体检系统 | 体检人员、套餐、申请 | 结果、报告状态 | REST/文件批量 |
| 收费系统 | 收费确认、退费、冲正 | 计费触发、执行状态、对账 | HIS 计费接口；LIS 不保存财务总账 |
| 分析仪/流水线 | 结果、质控、设备状态 | 工作列表、样本项目 | ASTM、HL7 v2 MLLP、文件、串口桥接 |
| CA/电子签名 | 证书、签名服务 | 报告摘要、签名请求 | 厂商 SDK/REST |
| 统一认证 | 用户、组织、角色声明 | 登录审计 | SAML/OIDC/LDAP |
| 消息平台 | 回执 | 危急值、报告通知、接口告警 | 医院消息总线、短信、企业微信等 |
| 区域平台 | 患者/医嘱/转诊 | DiagnosticReport、Observation、Specimen、质量数据 | FHIR R4 优先 |

### 7.3 需要新增的核心数据对象

- `encounter`：门诊、住院、体检、急诊等就诊上下文。
- `external_order_identity`：外部申请单、医嘱、执行单和版本。
- `specimen_event`：采集、运输、交接、签收、拒收、重采、分发、处置事件。
- `interface_message`：原文、标准化内容、处理状态、错误、重试、回执、关联业务对象。
- `terminology_mapping`：医院项目、组合、样本、科室、医生、单位和 OpenELIS 字典映射。
- `critical_value_event`：复核、通知对象、通知方式、确认、处理反馈、升级和关闭。
- `report_version`：报告版本、修订原因、签名、发布、撤回、通知和回执。
- `billing_event`：收费确认、计费、退费、冲正、对账状态，不保存医院财务总账。
- `device_maintenance_event`：校准、保养、故障、停机、恢复和放行。

### 7.4 建设、复用、外接和暂缓

| 策略 | 范围 |
| --- | --- |
| 当前项目内建设 | 任务中心、统一状态机、样本事件、拒收重采、结果/审核/报告闭环、危急值、报告版本、接口台账、码表映射、中文产品包 |
| 复用并产品化 | 患者、订单、条码、分析仪、QC、EQA、CAPA、库存、存储、转诊、FHIR、RBAC、审计 |
| 外部对接 | HIS/EMR/体检、收费结算、CA、统一认证、短信/企业微信、叫号、互联网医院 |
| 暂缓或独立项目 | 全院财务、HRP、药房、完整患者门户、血库、复杂微生物、POCT、AI 诊断 |

## 8. 分阶段路线图

### 阶段 M0：产品基线与试点定义

交付物：

- 选定试点医院、科室、专业组、日样本量和首批分析仪。
- 完成患者、就诊、项目、组合、样本、试管、科室、医生和收费码表清单。
- 获取 HIS、收费、CA 和分析仪接口文档及测试环境。
- 选取 20 条真实匿名业务案例作为验收数据集。

退出条件：医院、实验室、信息科和项目组签署同一份范围与接口清单。

### 阶段 M1：单院最小可用闭环（P0）

范围：

- 角色工作台和任务导航。
- 电子医嘱/手工开单、采样、签收、拒收重采。
- 工作计划、手工/仪器结果、审核、报告发布。
- 中文主数据、报告模板、岗位角色包。
- 订单—样本—结果—报告全链审计。

退出条件：匿名测试订单可从申请连续走到报告发布；任何一步都能看到状态、责任人、阻断原因和下一步。

### 阶段 M2：接口与设备可运营（P0）

范围：

- HIS/EMR、护士站、收费、报告回传。
- 接口配置、码表、消息台账、失败重试和对账。
- 首批 3—5 个代表性分析仪真实联机。
- 分析仪未匹配结果隔离、人工映射和重放。

退出条件：医嘱和报告往返成功；接口中断恢复后可自动或人工补偿，不丢单、不重复建单。

### 阶段 M3：医疗安全和质量闭环（P0/P1）

范围：

- 危急值闭环、报告撤回修订、电子签名。
- IQC 失控阻断、复检/Delta/自动审核首批规则。
- TAT、拒收率、危急值及时率、接口成功率看板。
- 设备维护与停机状态。

退出条件：危急值、质控失控、报告修订均能完整演示并留下可审计证据。

### 阶段 M4：规模化和差异化（P1/P2）

范围：

- 门诊采血、叫号、移动采集。
- 区域样本转诊、冷链运输、中心实验室分发。
- 微生物、POCT 等专业域。
- 主任办公、成本、产能、区域质量分析。

退出条件：完成至少一个院内扩科或区域协同场景，不依赖复制一套新代码。

### 8.1 建议优先级

**P0——不完成就不能称为医院可交付 LIS**

1. HIS 医嘱与报告回传。
2. 就诊/病区/床位和中国患者上下文。
3. 采样—运输—签收—拒收—重采闭环。
4. 结果—审核—报告发布闭环。
5. 危急值闭环。
6. 报告版本、撤回、修订和签名。
7. 接口台账、码表、重试、对账。
8. 代表性分析仪真实联机。
9. 收费状态和计费事件协同。
10. 中文主数据、报告、错误和培训资料。
11. 权限、审计、备份恢复和上线验收。

**P1——显著提升效率和规模化能力**

- 门诊采血与叫号、自动审核、Delta Check、复检规则、TAT SLA、设备维护、试剂批次联动、患者报告推送、主任办公。

**P2——形成差异化**

- 区域医共体、移动采集、复杂微生物、POCT、跨机构检验互认、智能排程和本地隐私保护分析助手。

## 9. 验收指标

指标最终阈值应与试点医院确认，以下为建议基线：

| 维度 | 指标 |
| --- | --- |
| 完整性 | 订单、样本、结果、报告和关键异常均能通过统一业务号追踪 |
| 接口 | 正常消息最终处理成功率 ≥ 99.5%；失败消息 100% 可查询、可重试 |
| 幂等 | 重复医嘱或重复结果不得生成重复业务对象 |
| 样本 | 采集、交接、签收、拒收、重采、分发事件记录率 100% |
| 分析仪 | 经过映射的正常结果自动匹配率建议 ≥ 98%，其余进入隔离队列 |
| 危急值 | 100% 记录复核、通知、确认、处理反馈和超时升级 |
| 报告 | 所有修订保留原版本、原因、签名、通知和回执 |
| 权限 | 每个岗位仅可访问授权患者、科室和操作；敏感操作可审计 |
| 可用性 | 新用户经角色培训后可独立完成一条核心闭环；主页面不依赖多入口猜测 |
| 中文 | P0 流程无影响业务理解的英文残留，主数据和报告符合医院术语 |
| 运维 | 完成备份、恢复、接口断线、设备断线、服务重启和升级回滚演练 |
| 测试 | 核心流程具备自动化端到端测试，真实设备和接口另有现场验收证据 |

## 10. 团队与实施建议

建议最小核心团队：

- 产品经理/医疗业务分析 1 人；
- 检验科业务专家 0.5—1 人；
- 前端 1—2 人；
- 后端/领域开发 2 人；
- 接口与设备工程 1—2 人；
- 测试/实施 1 人；
- DevOps/安全 0.5 人。

在有医院测试环境、接口文档和分析仪支持的前提下，单院常规检验试点通常应按 **4—6 个月**准备，而不是把“页面能打开”视为上线完成。时间最大变量不是编码量，而是医院主数据清洗、厂商联调、分析仪真实报文、角色验收和平行运行。

建议上线策略：

1. 先用匿名数据和模拟接口跑完整闭环。
2. 再接一个 HIS 测试科室和一台代表性分析仪。
3. 完成危急值、报告修订、接口中断和备份恢复演练。
4. 选择有限专业组进行平行运行，结果与原系统逐单核对。
5. 达到验收指标后再扩科、扩设备和扩机构。

## 11. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 金唐公开资料有限 | 竞品细节可能不完整 | 安排厂商演示或医院用户访谈，以本方案矩阵逐项询证 |
| 医院接口高度私有 | 工期被定制接口吞噬 | 建适配器、标准模型、码表和消息台账，不把私有字段写进核心业务 |
| 分析仪协议与说明书不一致 | 结果丢失或错配 | 真实报文回放、双向对账、隔离队列、逐设备验收 |
| 主数据质量差 | 医嘱无法匹配、参考范围错误 | 上线前冻结字典版本，建立映射审核与差异报告 |
| 新旧页面并存 | 用户误操作、培训困难 | 每个任务保留一个主入口，旧入口只做兼容并逐步退场 |
| 危急值和报告修订不闭环 | 医疗安全风险 | P0 强制验收，不允许以人工电话或纸面流程替代系统证据 |
| 范围扩张到完整 HIS/HRP | 产品失焦 | 明确 LIS 边界；收费、CA、认证、患者门户以外接为主 |
| 只做功能不做实施 | 无法交付 | 把角色验收、培训、运维、数据、设备和接口纳入同一里程碑 |

---

## 12. 最终建议

1. **继续基于当前 OpenELIS 开发是合理的。** 现有实验室、质量、样本、分析仪和标准化底座足以支撑产品化，不需要重写核心 LIS。
2. **首要目标不是追平所有菜单，而是补齐七个关键闭环。** 尤其是 HIS、拒收重采、危急值、报告修订、分析仪异常、质控失控和收费事件。
3. **把医院差异放到接口和配置层。** 建立统一消息台账和码表映射后，后续医院才能复制交付。
4. **先做单院常规检验最小闭环，再做区域和专业扩展。** 不建议首期同时承诺复杂微生物、POCT、血库和完整患者门户。
5. **下一研发主线应从当前 M2 订单闭环继续推进到 M3 结果/审核/报告，再立即进入 M4 医院接口底座。** 这些工作完成前，不应把产品描述为可替代成熟国产 LIS 的最终交付版。

## 13. 下一步可执行事项

- 取得 HIS/EMR、收费、CA 和分析仪接口文档，完成接口工作量评估。
- 继续完成当前订单四步闭环，并建立从电子医嘱到报告回传的第一条端到端自动化测试。
