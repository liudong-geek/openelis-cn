# 保存核对读取事务边界：限定验收（2026-09-13）

## 业务目标与本批范围

接续最新版 v3 的“保存核对 → 当前申请及完整逐管状态读回 → 明确恢复采集”。先解决已确认的前置问题：普通 JPA 事务不能直接使用拟议的重复读隔离级别；即使写 REQUIRES_NEW，只有预绑定实体上下文、没有活动外层事务时，仍可能沿用旧缓存。

本批仅为既有 `EntrySubmissionService.recover` 建立专用读取边界，不增加菜单、第二套回执、current 接口或浏览器解除保护。首次 `submit`、默认事务管理器、实体工厂、原 persistence provider 和全局连接策略保持原样。

实现限定：

- 配置命名事务管理器，与原管理器使用同一实体工厂和数据源作为资源键；仅创建恢复查询使用的新 Hibernate Session，并在创建前指定 HOLD 连接模式。
- 恢复入口显式指定 REQUIRES_NEW、REPEATABLE_READ、readOnly、20 秒及受检异常回滚。活动外层事务由 Spring 挂起和恢复；恢复结束关闭新上下文。
- 若没有活动外层事务、仍预绑定实体上下文，拒绝进入恢复；不清空、关闭、解除绑定或复用其他流程的缓存及待保存内容。
- Session 创建后、交给 Spring 管理前的校验失败自行关闭新 Session；交接后的开始、提交及结束由原 Spring/JPA 生命周期管理，不自行另写 JDBC/SQL 或手动绑定上下文。
- 新事务定义检查只作用于 `doBegin`；不能概括为“命名管理器可拒绝所有参与既有事务的误用”。实际入口固定 REQUIRES_NEW，由入口级回归保障。

## 产品与交付边界

浏览器仍显示“核对历史保存记录”的既有语义；**历史管的 REQUESTED 不代表现在未采集**。本批没有前端改动或新的浏览器验收，没有用历史快照恢复表单、清除未知标记、开放编辑或继续采集。

这些证据只确认恢复读取的限定事务适配。真实 PostgreSQL 快照一致性、并发/权限变更、迁移、驱动及连接池清理尚未验。尤其开始失败后 Spring 会关闭新连接，但不能用 mock 的 close 推断真实池已复位；部分驱动的只读设置错误可能被框架容忍，清理错误也可能只记录日志，不宣称驱动层强制只读或所有异常都恢复连接属性。

下一主批：复用此边界实现当前申请、患者、全部逻辑请求（含取消）、全部物理管（含作废）及实际检验项目的一致读回；结合原提交者及完整当前权限拒绝缺项、错关联和冲突，随后接前端明确确认采用。不得拼接两个旧 GET 或把历史回执当当前状态。获准隔离库需验证真实保存 → 读回 → 采集及异常并发；报告 P0、AC09/AC14 整体、M0～M7和发布门禁均未关闭。

本轮未启动/变更 Docker、业务数据库、真实患者、设备、报告签发、打印或 18080；未推送。源码存档和本地提交只是代码检查点，不是数据库/配置备份或可运行回退版本。
